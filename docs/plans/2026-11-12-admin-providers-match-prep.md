# 方案：修复后台 AI 接口，并调整开局角色流程

日期：2026-11-12  
基线分支：`optimize/net-https-resume-lag`（commit `50fa0e1`）  
工作分支：`feature/admin-providers-match-prep`

线上后台报错 `crypto.randomUUID is not a function`，出现在 `http://107.175.30.198:18453/admin` 的「AI 接口」页。原因：`public/admin/admin.js` 在没有接口或点击「新增接口」时调用 `crypto.randomUUID()`；该 API 在非安全上下文（公网 HTTP）不可用。后台其实已支持自定义接口地址、协议、模型名称和 API Key，只是页面崩溃没法用。

本批完成以下事项后由维护者测试、提交并部署。不要提交、推送或改 git 历史，不要改云服务器，不要把密钥写入仓库。

## 1. 修复 AI 接口页，并保证自定义模型可用

1. 增加可在 HTTP 下工作的 id 生成函数（例如 `crypto.getRandomValues`，再降级到足够随机的备用实现）。不要再直接调用 `crypto.randomUUID()`。检查 `public/admin/`、`public/avatar/` 及其他前端代码，同样替换。
2. 没有已保存接口时，打开「AI 接口」应直接显示可编辑的新建表单，而不是报错。字段保持：名称、协议（Responses / Chat Completions）、接口地址、模型名称、API Key。保存后密钥不明文回显。
3. 勾选「保存后将此接口用于玩家角色生成」并保存成功后，玩家生成角色必须使用该接口的地址、协议、模型和密钥。未测试通过不得启用的现有规则保留。
4. 补测试：在没有 `crypto.randomUUID` 的环境中打开/新增接口不抛错；启用后的生成请求打到所保存的 baseURL/model，且不把密钥返回给前端。

## 2. 房间最多 8 人

- `Match.join` 上限由 4 改为 8，错误文案改为最多 8 人。
- 大厅、规则、人口显示、README 中所有「4 人 / 2—4」改为 8 / 2—8。至少 2 人开局不变。
- 地图已有 38 个出生点，不要随便改地图；8 人仍按现有出生点分散逻辑。
- 更新 `tests/match.test.js` 等所有按 4 人上限写的测试。

## 3. 每次开局只能生成一次角色

- 「开局」指即将开始或正在进行的这一局（含大厅准备和 `preparing`）。同一局每个玩家最多成功提交一次生成。失败可再试，成功后该局不能再生成。再来一局后计数清零，可再生成一次。
- 使用默认外观不占次数。管理员测试生成不受此限。
- 服务端强制拒绝第二次生成，客户端也禁用并说明「本局已生成过角色」。
- 对局中生成若仍开启，同样计入这一局的一次额度。

## 4. 关闭玩家 3D 预览后的开局流程

当后台「玩家 3D 预览」关闭时（`features.preview === false`）：

1. 玩家确认提示词后不再进入 3D 预览，也不再额外点「装备」。生成成功后自动装备该角色。可选择「使用默认外观」。
2. 房主点击开始后，房间进入 `preparing`，不要马上进入 `playing`。快照里带上准备截止时间、每位玩家的准备状态（默认 / 生成中 / 已完成 / 失败）。
3. 从进入 `preparing` 起最多等待 100 秒。若玩家在开始前已确认并完成生成，应直接算完成。全部已连接玩家都已完成（已装备本局生成角色或已选默认）后立即开局。
4. 100 秒到时仍未完成的任务取消或视为失败，这些玩家用默认外观，然后开局。不要无限等待。
5. 这一阶段最多允许房间内全部玩家同时生成（最多 8 路），不要被默认并发 2、每小时 6 次、15 秒间隔挡住这次开局生成。这 100 秒是开局等待上限；单独一次生成也应在 100 秒内结束或失败。
6. 准备期间新玩家仍不能加入进行中的准备/对局（保持现有「对局中不能新加入」；`preparing` 同样禁止新加入）。断线重连仍可回到准备中的房间身份。
7. 预览开启时，开局流程保持现在这样：大厅预览并装备，房主开始后直接进入比赛。预览关闭的说明要写进后台开关文案、玩家界面和 README。
